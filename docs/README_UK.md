# MikroTik Backup Script

**Резервне копіювання MikroTik RouterOS.**

Цей скрипт призначений для створення резервних копій пристроїв під керуванням RouterOS як у ручному, так і в автоматичному режимі за допомогою планувальника *(налаштовується окремо)*.
Файл `mikrotik-backup.sh` є самодостатнім скриптом, однак деякі його можливості можна змінити за допомогою файла `option.cfg`.

<br>

## Можливості скрипта

| Можливість | Як це працює |
|---|---|
| Режим одного пристрою | Створення копії одного пристрою за допомогою параметрів CLI |
| Пакетне оброблення | Послідовне оброблення пристроїв зі списку DeviceList; імпорт списку з Oxidized |
| Формати копій | На вибір: `.rsc`, `.backup` або обидва формати послідовно |
| Режими копій | На вибір: compact, terse, verbose; шифрування бінарних копій |
| Інкрементність | Можливість зберігати резервні копії лише за наявності змін |
| Щомісячний архів | Архівування старих копій і журналів на календарній межі |
| Журналювання | Загальні етапи записуються до `main.log`, а робота з пристроями — до `devicename.log` |
| Меню налаштування | Інтерактивне меню для зручного налаштування та використання |
| Локалізація | Вбудовані російська й англійська мови; підключення зовнішніх файлів локалізації |
| Сховище копій | Можна вибрати будь-який каталог для зберігання копій, зокрема NAS |
| Робота з NAS | Перевірка доступності сховища перед створенням резервної копії |

<br>

## Системні вимоги та початок роботи

**Обов’язково:**
GNU Bash 4.4 або новіший і встановлені утиліти **SSH**, **SCP** та **SSHPass**.
Утиліта **zip** потрібна лише для щомісячного архівування резервних копій. Усі необхідні утиліти й команди для їх установлення наведено в розділі [Залежності](uk/INSTALL.md#залежності).
*(N.B. Якщо немає утиліти, обов’язкової для потрібної операції, скрипт завершить роботу з помилкою. Це очікувана поведінка.)*

**Необов’язково:**
**autofs**, **davfs2**, **rclone** та інші засоби монтування зовнішніх накопичувачів.

**Установлення:**
Отримання файлів і підготовку до роботи описано в розділі [Установлення](uk/INSTALL.md).

У каталозі із завантаженими файлами виконайте:

Наведений нижче блок команд розрахований на файли з GitHub Release. У Git-клоні вихідного дерева згенерованого `SHA256SUMS` немає; для такого варіанта починайте з `chmod 700 mikrotik-backup.sh`, а потім виконуйте перевірки версії та довідки.

```bash
sha256sum -c SHA256SUMS &&
chmod 700 mikrotik-backup.sh &&
./mikrotik-backup.sh --language en --version &&
./mikrotik-backup.sh --language ru --help
```

Якщо перевірка контрольної суми завершилася помилкою, **не запускайте файл!!!**

## Способи запуску

**Запуск файла БЕЗ додаткових параметрів** *(коли `option.cfg` немає або він непридатний)*
Якщо поруч зі скриптом немає `option.cfg` або файл не містить жодного придатного налаштування, відкриється Configuration Editor для створення або редагування `option.cfg`.

**Запуск файла БЕЗ додаткових параметрів** *(коли є справні `option.cfg` і `devicelist.cfg`)*
Якщо придатні налаштування вже є, скрипт перейде до пакетного резервного копіювання.

**Запуск скрипта з параметром:**

| Завдання | Команда |
|---|---|
| Відкрити інтерактивне меню | `./mikrotik-backup.sh -i` |
| Відкрити BackUP Master | `./mikrotik-backup.sh -b` |
| Створити або змінити `option.cfg` | `./mikrotik-backup.sh -e` |
| Показати повну довідку щодо параметрів CLI | `./mikrotik-backup.sh -h` |
| Виконати запуск для одного пристрою | Повна CLI-трійка: адреса пристрою, користувач і пароль |

Найважливіший тут параметр `-i`: він відкриває інтерактивне меню, у якому можна:

- за допомогою BackUP Master ввести параметри пристрою, створити його резервні копії та створити або доповнити `devicelist.cfg` вибраними параметрами;
- за допомогою Configuration Editor створити або відредагувати файл параметрів `option.cfg`;
- переглянути довідку щодо параметрів CLI;
- прочитати коротку інструкцію про можливості скрипта.

Повну довідку щодо параметрів CLI, зокрема точних форм `-a=...`, `-u=...` і `-p=...`, дивіться в [Довіднику командного рядка](uk/CLI.md).

## Де зберігаються результати, або «Де мої бекапи???»

За замовчуванням резервні копії пристроїв зберігаються в каталозі `backups` поруч зі скриптом. Якщо такого каталогу ще немає, скрипт створить його самостійно.
*(N.B. Відносний шлях `backups` відлічується саме від каталогу скрипта, а не від поточного робочого каталогу!)*

У режимі одного пристрою окремий підкаталог для нього не створюється:

```text
backups/
├── main.log
├── Router-A_YYYY-MM-DD_HH-MM.rsc
├── Router-A_YYYY-MM-DD_HH-MM.backup
└── Router-A_YYYY-MM-DD_HH-MM.log
```

У пакетному режимі кожен пристрій має власний каталог:

```text
backups/
├── main.log
└── Router-A/
    ├── Router-A_YYYY-MM-DD_HH-MM.rsc
    ├── Router-A_YYYY-MM-DD_HH-MM.backup
    ├── Router-A.log
    └── archive/
        └── DD.MM.YYYY.zip
```

Це приклади розміщення, а не обов’язковий набір файлів після кожного запуску.
Журнал створюється під час першого придатного для запису повідомлення.
Параметр `MainLogPath` у файлі `option.cfg` дає змогу перенести `main.log`, наприклад до `/var/log/` або будь-якого іншого зручного каталогу.
Докладні налаштування каталогів резервних копій, архівів і журналів наведено в розділі [Конфігурація](uk/OPTIONS.md).

## Щомісячне архівування

За замовчуванням цю можливість вимкнено. Якщо скрипт запускається за розкладом, параметр `MonthlyArchive=true|1...28` у файлі `option.cfg` дає змогу вибрати момент архівування всіх резервних копій за попередній період.

У пакетному режимі порядок роботи цього дня змінюється: спочатку архівуються всі придатні дані, накопичені в каталозі резервних копій, і лише потім створюються копії за поточну дату.

Архів отримує ім’я попереднього календарного дня: наприклад, під час запуску 1 жовтня це буде `30.09.YYYY.zip`.

*(N.B. Якщо розклад НЕ щоденний, для цієї можливості потрібно створити окреме завдання на потрібну дату. Якщо скрипт запускається щодня або частіше, окреме завдання не потрібне.)*

Пропущена щомісячна спроба, незалежно від причини, не наздоганяється щоденними запусками.
Наступна штатна спроба збирає всі накопичені старі дані в один архів, навіть якщо вони належать до кількох місяців. `main.log` не архівується.

Повні правила, приклади й наслідки помилок цього режиму наведено в розділі **[Щомісячні архіви](uk/BACKUPS.md#monthly-archive)**.

## Межі застосування

Скрипт створює резервні копії, але не відновлює конфігурацію маршрутизатора.
У поточній версії він не надсилає сповіщень електронною поштою або через месенджери й не видаляє старі ZIP-файли за віком.
Процедуру відновлення, зовнішню ротацію та контроль результатів організовує адміністратор.

Профіль SSH використовує парольну автентифікацію та вимкнену перевірку ключа сервера.
Шифрування `.backup` не шифрує `.rsc`, файли конфігурації або ZIP-архіви.
Перед використанням у робочому середовищі прочитайте [модель безпеки](uk/SECURITY.md).

# Установлення

[Зміст](../README_UK.md)

## Вимоги до хоста

Для запуску потрібна ОС Linux із GNU Bash **4.4 або новішим** і стандартними утилітами GNU для роботи з файлами.
Сам скрипт не потребує компіляції, Python, контейнера чи бази даних.
Однак потрібні утиліти, перелічені в розділі [Залежності](#залежності).

Для імен пристроїв потрібна працездатна локаль **`C.UTF-8`**: вона забезпечує підрахунок багатобайтових символів, розпізнавання літер і зміну регістру.
Скрипт перевіряє ці можливості перед роботою з пристроями. Це системна вимога, а не окрема програма з назвою `C.UTF-8`.

Звісно, хост повинен мати заздалегідь налаштований мережевий доступ до служби SSH RouterOS і право запису до вибраного сховища.

**Наполегливо рекомендовано!!!**
Для підключення до пристроїв RouterOS використовується SSH із парольною автентифікацією, а не автентифікацією за ключами.
*(Точну транспортну політику дивіться в [SECURITY.md](SECURITY.md).)*
Тому на пристрої варто створити окремого користувача й обмежити його вхід IP-адресою хоста, на якому виконується цей скрипт.

## Залежності

### Обов’язкові для резервного копіювання

Для резервного копіювання потрібні **всі** перелічені утиліти:

| Утиліти | Призначення |
|---|---|
| `ssh`, `scp`, `sshpass` | Підключення до RouterOS, виконання команд і отримання файлів |
| GNU `timeout`, `sleep` | Обмеження тривалості операцій і паузи |
| `sha256sum` | Обчислення контрольних сум |
| `realpath` | Визначення абсолютних шляхів |
| `flock` | Блокування, що запобігають конфліктам одночасних запусків |

**Якщо обов’язкової утиліти немає, скрипт повідомляє про незадоволені залежності й припиняє спробу резервного копіювання. Код помилки залежностей — `30`. Це штатна поведінка.**

Список однаковий для режиму одного пристрою та пакетного копіювання незалежно від того, створюється `.rsc`, `.backup` чи обидва формати.

Самої наявності команд недостатньо: установлений OpenSSH має підтримувати використані параметри, зокрема застарілий режим SCP, який вибирається через `scp -O`.
GNU `timeout` має підтримувати `--signal` і `--kill-after`.
Ці можливості перевіряються локально, без підключення до маршрутизатора.

<br />

### Потрібні для окремих можливостей

Ці інструменти не входять до загального обов’язкового списку. Вони потрібні лише тоді, коли використовується відповідна можливість.

| Можливість | Що потрібно | Що відбудеться за відсутності |
|---|---|---|
| Пакетний режим із `UseNetFolder=true` | `findmnt` | Резервне копіювання в цьому режимі не почнеться; помилка залежностей `30` |
| Запуск, у якому має відбутися щомісячне архівування | Info-ZIP `zip`, `unzip`, GNU `mv` | Запуск зупиниться на перевірці залежностей до резервного копіювання; помилка `30` |
| Інтерактивне меню, Configuration Editor і BackUP Master | `stty` і термінал на стандартному введенні та виведенні | Інтерактивний екран не відкриється; помилка термінала `31` |
| **Copy console command** у BackUP Master | GNU `base64` із підтримкою `--wrap=0` | Команду неможливо скопіювати; помилка `30` |

Наприклад, відсутність `zip` не заважає звичайному резервному копіюванню, якщо цього запуску щомісячне архівування не потрібне.
Відсутність `base64` не заважає створювати резервні копії.
*(N.B. Вона потрібна, коли вибрано дію **Copy console command**.)*

Загальна перевірка залежностей виконується перед резервним копіюванням, а не щоразу під час відкриття програми.
Тому довідка, відомості про версію або меню можуть бути доступні навіть без установлених утиліт резервного копіювання.

<br />

### Базове середовище Linux

Також передбачається наявність звичайних системних команд для роботи з файлами й каталогами, зокрема `date`, `stat`, `mkdir`, `cp`, `ln` і `rm`.

Вони є частиною базового середовища ОС. Наведений вище список залежностей, які перевіряються заздалегідь, не охоплює всіх зовнішніх команд, що використовує скрипт. Відсутність базової системної команди може проявитися як помилка відповідної операції, а не як повідомлення про незадоволені залежності.

<br />

### Установлення потрібних пакетів у Debian/Ubuntu

Приклад установлення обов’язкових і перелічених додаткових інструментів:
*(N.B. Тут і далі вважається, що користувач має права адміністратора.)*

sudo apt-get update
sudo apt-get install bash openssh-client sshpass coreutils util-linux zip unzip

## Отримання файлів скрипта

Основний спосіб установлення версії 2.3.1 — повний asset GitHub Release `mikrotik-backup-2.3.1.zip`. Він розпаковується безпосередньо в каталог установлення без додаткового каталогу-обгортки.
*(N.B. У прикладах із розміщенням файлів у `/opt` виконуйте команди з правами на створення цього каталогу та запис до нього.)*

### Варіант 1. Повний пакет випуску

Завантажте `mikrotik-backup-2.3.1.zip` з GitHub Release MikroTik Backup Script 2.3.1 і виконайте:

```bash
mkdir -m 700 -- /opt/mikrotik-backup
unzip -q -- mikrotik-backup-2.3.1.zip -d /opt/mikrotik-backup
cd -- /opt/mikrotik-backup
sha256sum --check SHA256SUMS
```

Після розпакування готова до роботи структура має вигляд:

```text
mikrotik-backup.sh
SHA256SUMS
README.md
lang/
docs/
```

Якщо перевірка контрольної суми завершується помилкою, не запускайте скрипт, доки не з'ясуєте причину.

<br />

### Варіант 2. Мінімальне автономне встановлення

Завантажте assets `mikrotik-backup.sh` і `SHA256SUMS` з того самого Release до захищеного каталогу, перевірте їх і зробіть скрипт виконуваним:

```bash
mkdir -m 700 -- /opt/mikrotik-backup
cd -- /opt/mikrotik-backup
# Завантажте обидва assets випуску до цього каталогу.
sha256sum --check SHA256SUMS
chmod 700 -- mikrotik-backup.sh
```

Для зовнішньої runtime-мови використовуйте повний пакет або отримайте відповідний файл `.lang` з позначених тегом вихідних файлів тієї самої версії.

<br />

### Розширений варіант: Git або архів вихідного коду

Git-клон або архів **Code → Download ZIP** цього репозиторію також є повним деревом вихідного коду продукту. Корисна структура в корені:

```text
mikrotik-backup.sh
README.md
lang/
docs/
```

`SHA256SUMS` є артефактом Release і може бути відсутнім у копії вихідного коду. Для звичайного встановлення й надалі рекомендується версійний пакет Release, оскільки він містить файл контрольних сум і точно відповідає опублікованій версії.

## Файли поруч зі скриптом

Після розпакування повного пакета Release вибраний каталог містить скрипт і супровідні файли:

```text
mikrotik-backup/
├── mikrotik-backup.sh
├── SHA256SUMS
├── README.md
├── lang/
└── docs/
```

| Файл або каталог | Призначення |
|---|---|
| mikrotik-backup.sh | Сам скрипт резервного копіювання |
| SHA256SUMS | Контрольні суми для перевірки отриманих файлів |
| README.md | Опис програми й посилання на докладну документацію |
| lang/ | Набір файлів локалізації. Скопіюйте потрібний мовний файл із цього каталогу до каталогу скрипта. |
| docs/ | Докладна документація щодо встановлення, налаштування та використання |

Для практичної роботи потрібен лише файл `mikrotik-backup.sh`.
Щоб змінити налаштування, створіть **option.cfg** і розмістіть його поруч зі скриптом.
Якщо планується послідовно опитувати кілька пристроїв і створювати їхні резервні копії, також створіть поруч зі скриптом файл списку пристроїв **devicelist.cfg**.
Файл локалізації `<xx>.lang` потрібен, якщо ви хочете бачити меню й записи журналів своєю мовою. Його також слід розмістити в каталозі з `mikrotik-backup.sh`.
Для російської та англійської мов окремий файл локалізації не потрібен: вони вбудовані в скрипт.

**В інтерактивному режимі скрипт може створити й зберегти:**
список пристроїв — **devicelist.cfg** через BackUP Master;
файл конфігурації — **option.cfg** через Configuration Editor.
Їх також можна підготувати самостійно:
*Файл списку пристроїв у форматі TSV докладно описано в [DEVICES.md](DEVICES.md).*
*Файл конфігурації у форматі `Ключ=значення` докладно описано в [OPTIONS.md](OPTIONS.md).*

## Підготовка сховища та журналів

За стандартних налаштувань резервного копіювання скрипт створює поруч із собою каталог `./backups` і зберігає в ньому резервні копії пристроїв.
Різниця між режимами лише в тому, що під час запуску для одного пристрою створені файли розміщуються безпосередньо в `./backups`, а в пакетному режимі всередині `./backups` створюється підкаталог з іменем пристрою, до якого й зберігаються його резервні копії.

Потрібні каталоги сховища скрипт створює самостійно з відповідними правами доступу.
*(Власника й режим доступу вже наявних адміністраторських каталогів скрипт автоматично не змінює.)*

За замовчуванням основний журнал скрипта, `main.log`, розміщується в `./backups`.
У пакетному режимі журнал роботи з пристроєм міститься в підкаталозі цього пристрою.

Якщо каталог резервних копій розміщено в мережевому сховищі, скрипт у пакетному режимі може перевіряти його доступність. За замовчуванням цю можливість вимкнено, і перед використанням її потрібно налаштувати.
*(Спосіб монтування каталогу не має значення.)*

Усі ці параметри можна змінити у файлі `option.cfg`.
Їхній синтаксис і спосіб налаштування наведено в розділі [Конфігурація](OPTIONS.md).

## Автоматичний запуск скрипта

Перед увімкненням розкладу потрібно підготувати налаштування та список пристроїв.
Інакше автоматичний запуск не зможе виконати пакетне копіювання.

Створювати окремого користувача для запуску скрипта не обов’язково, однак виконувати подібні операції від **root** вважається поганою практикою. Нижче показано варіант з окремим користувачем.

Створіть користувача **bsmt** *(можна вибрати інше ім’я, замінивши **bsmt** у прикладах)* і надайте йому лише мінімально потрібні права:

```bash
(
    set -e

    SCRIPT_DIR="/opt/mikrotik-backup"

    sudo useradd \
        --system \
        --user-group \
        --home-dir "$SCRIPT_DIR" \
        --no-create-home \
        --shell /usr/sbin/nologin \
        bsmt

    sudo chown bsmt:bsmt \
        "$SCRIPT_DIR" \
        "$SCRIPT_DIR/mikrotik-backup.sh"

    sudo chmod 0700 \
        "$SCRIPT_DIR" \
        "$SCRIPT_DIR/mikrotik-backup.sh"

    sudo find "$SCRIPT_DIR" -maxdepth 1 -type f \
        \( -name 'option.cfg' -o -name 'devicelist.cfg' -o -name '*.lang' \) \
        -exec chown bsmt:bsmt {} + \
        -exec chmod 0600 {} +
)
```

<br />

**Якщо скрипт уже запускався від root**

*(N.B. Якщо раніше ви запускали скрипт від **root**, створені ним каталоги, резервні копії та журнали можуть бути недоступні користувачеві **bsmt**. Перед увімкненням розкладу передайте йому наявне сховище.)*

Цей приклад використовує локальний каталог `/opt/mikrotik-backup/backups`.
Наведена команда змінює власника й групу каталогу та всього його вмісту:

```bash
sudo chown -hR -P -- bsmt:bsmt "/opt/mikrotik-backup/backups"
```

*(N.B. Указуйте саме каталог резервних копій цього скрипта, а не спільний каталог, що містить дані інших програм. Якщо сховище або основний журнал розміщено окремо, доступ до кожного з них потрібно налаштувати окремо з урахуванням прав і параметрів вибраного сховища за наведеним вище зразком.)*

Приклад відкриття Configuration Editor від імені **bsmt** після надання йому прав на каталог і файли скрипта:
*(N.B. Команду виконує root або користувач, якому дозволено такий запуск через sudo.)*

```bash
sudo -u bsmt /usr/bin/bash /opt/mikrotik-backup/mikrotik-backup.sh -e
```

**Створення розкладу запуску скрипта**

Нижче розглянуто створення розкладу за допомогою systemd, але можна скористатися crontab або будь-яким іншим зручним способом.

Створимо сервіс, що виконує скрипт від нашого користувача, і таймер, який запускає його за розкладом.
*(У прикладі задано щоденний запуск о першій ночі, але розклад повністю залежить від вас.)*

```bash
(
    set -e

    sudo tee /etc/systemd/system/mikrotik-backup.service >/dev/null <<'EOF'
[Unit]
Description=MikroTik backup
Wants=network-online.target
After=network-online.target

[Service]
Type=oneshot
User=bsmt
Group=bsmt
WorkingDirectory=/opt/mikrotik-backup
ExecStart=/usr/bin/bash /opt/mikrotik-backup/mikrotik-backup.sh
Environment="PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"
UMask=0077
NoNewPrivileges=true
Restart=no
TimeoutStartSec=infinity
StandardInput=null
StandardOutput=journal
StandardError=journal
EOF

    sudo tee /etc/systemd/system/mikrotik-backup.timer >/dev/null <<'EOF'
[Unit]
Description=Daily MikroTik backup

[Timer]
OnCalendar=*-*-* 01:00:00
AccuracySec=1s
Persistent=false
Unit=mikrotik-backup.service

[Install]
WantedBy=timers.target
EOF

    sudo chmod 0644 \
        /etc/systemd/system/mikrotik-backup.service \
        /etc/systemd/system/mikrotik-backup.timer

    sudo systemd-analyze verify \
        /etc/systemd/system/mikrotik-backup.service \
        /etc/systemd/system/mikrotik-backup.timer

    sudo systemctl daemon-reload
    sudo systemctl enable --now mikrotik-backup.timer

    systemctl list-timers --all mikrotik-backup.timer
)
```

*`Persistent=false` не вмикає наздоганяльний запуск після періоду, коли таймер був вимкнений.
`Restart=no` не призначає автоматичних перезапусків сервісу після помилки.*

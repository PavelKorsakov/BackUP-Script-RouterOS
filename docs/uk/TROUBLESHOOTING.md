# Діагностика

[Зміст](../README_UK.md)

## З чого почати

Якщо резервне копіювання не почалося або завершилося помилкою, спершу перегляньте журнали. У `main.log` містяться загальні етапи роботи, а подробиці копіювання конкретного пристрою записуються до його окремого журналу.

Шукайте записи з позначкою `[ER]` і кодом помилки. Коди пояснено [нижче](#result-codes), а розташування журналів описано в [LOGGING.md](LOGGING.md).

Версію встановленого скрипта й довідку щодо параметрів можна отримати командами:

```bash
mikrotik-backup.sh --version
mikrotik-backup.sh --help
```

Щоб повторно запустити вже налаштоване пакетне копіювання з докладним виведенням:

```bash
mikrotik-backup.sh --log-level=3
printf 'Код завершення: %s\n' "$?"
```

Друга команда показує результат завершеного запуску. Рівень журналювання в `option.cfg` при цьому не змінюється.

## Скрипт не починає резервне копіювання

### Замість копіювання відкрився редактор

Під час запуску без параметрів це означає, що поруч зі скриптом немає `option.cfg` або в ньому немає придатних налаштувань. Порожній файл, самі коментарі або невідомі параметри не змінять ситуації.

Відкрийте Configuration Editor, виберіть потрібні налаштування, збережіть файл і запустіть скрипт повторно:

```bash
mikrotik-backup.sh -e
```

Збереження пристрою через BackUP Master створює `devicelist.cfg`, але не замінює підготовку `option.cfg`.

*(N.B. Якщо такий запуск відбувається з планувальника, редактор відкрити не вдасться, і скрипт завершиться з кодом `31`. Налаштування для автоматичного запуску потрібно підготувати заздалегідь.)*

### Помилка параметрів, код 12

Перевірте написання параметрів, їхні значення та поєднання дій. Причиною можуть бути невідомий параметр, порожнє значення, кілька різних дій одночасно або неповні облікові дані для підключення одного пристрою.

Для CLI-запуску одного пристрою потрібні адреса, логін і пароль. Відсутні облікові дані з `option.cfg` не підставляються.

Короткі параметри підключення записуються лише через `=`: `-a=`, `-u=`, `-p=`. При цьому `-p` задає пароль, а для SSH-порту використовується `--port`.

Усі допустимі параметри та приклади наведено в [CLI.md](CLI.md).

### option.cfg не читається, код 21

Перевірте, що `option.cfg` є звичайним файлом і доступний для читання користувачеві, від якого запускається скрипт. Також дозволено читабельне символічне посилання на такий файл.

Відсутність файла й неможливість його прочитати — різні ситуації. Якщо файл існує, але недоступний, скрипт не продовжить роботу зі стандартними налаштуваннями.

### Не знайдено залежність, код 30

Перевірте наявність основних утиліт:

```bash
command -v ssh scp sshpass timeout sleep sha256sum realpath flock
```

Для пакетної роботи з `UseNetFolder=true` також потрібен `findmnt`. У день щомісячного архівування потрібні `zip`, `unzip` і GNU `mv`. Для копіювання консольної команди з BackUP Master потрібен GNU `base64` із підтримкою `--wrap=0`.

**Самої наявності утиліти недостатньо.** Установлений OpenSSH має підтримувати використані параметри й `scp -O`, а GNU `timeout` — `--signal` і `--kill-after`.

Повний перелік залежностей і команди встановлення наведено в [INSTALL.md](INSTALL.md#залежності).

### Меню не відкривається, код 31

Меню, Configuration Editor і BackUP Master потребують термінала та працездатної утиліти `stty`. Не запускайте їх через канал або з перенаправленням стандартного введення чи виведення.

Якщо повідомлення вказує на недостатній розмір термінала, збільште вікно. Основним екранам потрібна ширина щонайменше 46 стовпців, а вбудованій інструкції — 80. У Configuration Editor і BackUP Master довгий список прокручується стрілками; уся форма не мусить уміщатися на екрані одночасно.

Керування інтерфейсом описано в [INTERACTIVE.md](INTERACTIVE.md).

## Список пристроїв не завантажується

### Файл devicelist.cfg, коди 22 і 23

Перевірте розташування файла й доступ до нього. `devicelist.cfg` має бути поруч із `mikrotik-backup.sh` незалежно від каталогу, з якого запускається скрипт.

Поля розділяються справжнім символом табуляції (TAB), а не пробілами. Для пристрою мають бути визначені ім’я, адреса, логін, пароль і допустимий SSH-порт. Спільні облікові дані можуть братися з `option.cfg`, якщо відповідні поля запису порожні.

Непридатний запис пропускається з попередженням. Якщо придатних пристроїв не залишилося, копіювати нічого, і скрипт завершиться з помилкою списку.

Також перевірте повторні підключення й однакові імена різних пристроїв. Формат файла, успадкування облікових даних і правила оброблення повторів описано в [DEVICES.md](DEVICES.md).

### Імпорт з Oxidized, коди 24 і 25

Код `24` означає проблему читання файлів `config` або `router.db` із каталогу `OxidizedHome`. Код `25` стосується їхнього вмісту: непідтримуваної схеми, помилкових даних або відсутності придатних пристроїв MikroTik.

Перевірте шлях, доступ до обох файлів, джерело `csv`, роздільник, карту стовпців і визначення моделі `routeros`. Дані читаються саме з `<OxidizedHome>/router.db`; параметр Oxidized `source.csv.file` не змінює цей шлях.

За `IgnoreOxiAccess=true` скрипт може продовжити роботу з попереднім придатним списком. Проте помилка імпорту однаково залишиться в результаті запуску. За `false` старий список у цьому запуску не використовується.

Налаштування імпорту описано в [DEVICES.md](DEVICES.md#імпорт-з-oxidized).

## Сховище та блокування

### Блокування зайняте, код 32

Перевірте, чи не працює вже інше завдання з тим самим каталогом резервних копій. Для запусків від одного користувача пакетне копіювання конфліктує з будь-яким іншим копіюванням у той самий `BackupRoot`. Два запуски для одного пристрою також не можуть виконуватися одночасно в цьому сховищі.

Дочекайтеся завершення активного завдання й повторіть запуск.

**Не видаляйте файли блокувань, щоб «звільнити» сховище.** Вони залишаються після завершення скрипта, а саме блокування утримує процес. Наявність файла в `/tmp/mikrotik-backup-${UID}/` ще не означає, що блокування зайняте.

### Немає доступу до каталогу

Перевірте шлях `BackupRoot`, права користувача, вільне місце й доступність самого накопичувача. Відносний шлях відлічується від каталогу скрипта. Кореневий каталог файлової системи `/` не можна використовувати для зберігання копій.

Якщо раніше скрипт запускався від root, а тепер працює від **bsmt**, попередні каталоги й файли можуть бути йому недоступні. Підготовку прав описано в [INSTALL.md](INSTALL.md#автоматичний-запуск-скрипта).

Для пакетної роботи з `UseNetFolder=true` потрібне окреме монтування. Перевірити його можна так:

```bash
findmnt -T /mnt/backup/mikrotik
findmnt -T /
```

Замініть перший шлях власним. Якщо обидва шляхи належать до того самого запису монтування, звичайний каталог у кореневій файловій системі не відповідає вимозі `UseNetFolder=true`. Сам скрипт сховище не монтує.

Код `64` означає помилку каталогу пристрою або його архіву за доступного спільного сховища. Оброблення інших пристроїв може продовжитися. Код `65` означає втрату або порушення стану спільного сховища й зупиняє решту пакетного оброблення.

Правила мережевого сховища описано в [OPTIONS.md](OPTIONS.md#network-storage).

## Помилки під час роботи з пристроєм

### SSH і передавання файлів, коди 40–43

Перевірте адресу пристрою, доступність його служби SSH, логін, пароль і порт. Якщо порт у `devicelist.cfg` не вказано, використовується `SshPort` із налаштувань, стандартне значення — `22`.

Користувач RouterOS повинен мати права на вибрані операції: експорт конфігурації, створення й отримання копій, видалення тимчасових файлів і ввімкнені очищення.

**І тут є нюанс!!!** Успішне підключення звичною командою SSH ще не означає, що скрипт використовує ті самі налаштування. Він працює з паролем і не використовує SSH-агент, ключі та звичайний `~/.ssh/config`. Файли отримуються через `scp -O`.

Код `40` стосується з’єднання або роботи транспортного каналу, `41` — автентифікації, `42` — команди RouterOS або її відповіді, `43` — передавання файла. Докладніше про параметри підключення дивіться в [SECURITY.md](SECURITY.md#підключення-до-routeros).

### Помилка імені, коди 50 і 52

Код `50` означає, що підсумкове ім’я пристрою непридатне. Перевірте вибране джерело імені та вміст дужок: у поточній версії для імені використовується саме перший завершений непорожній фрагмент у круглих дужках.

Після оброблення довжина має становити від 1 до 32 символів. Надто довге ім’я не обрізається. Зарезервовані імена на кшталт `CON` і `NUL` також заборонені.

Код `52` означає збіг підсумкового імені з іншим пристроєм у цьому запуску. Регістр під час порівняння не враховується: `Router-A` і `router-a` вважаються однаковими.

Джерело імені та правила його оброблення описано в [DEVICES.md](DEVICES.md#device-names).

### Копія не пройшла перевірку, коди 51 і 53

Код `51` стосується `.rsc`, а код `53` — `.backup`. Отриманий файл не пройшов перевірку: наприклад, він порожній або його розмір не збігається з розміром файла на пристрої.

Перегляньте, на якому етапі виникла помилка, і перевірте вільне місце та права як на хості, так і в RouterOS. Після невдалої спроби скрипт повторює її ще раз через 2 секунди. Спроби для двох форматів виконуються окремо, тому один файл може бути отримано успішно, а інший — ні.

Попередження про невдале видалення тимчасового файла з RouterOS після успішного отримання копії саме собою не означає, що локальну копію пошкоджено.

## Нової копії немає, але помилок теж немає

Спершу перевірте `UseIncremental`. Якщо порівняння ввімкнено, нову копію може бути видалено як повторну, а попередня залишиться. Для `.rsc` порівнюється вміст без дати у стандартному заголовку, для `.backup` — лише розмір файлів.

За `UseIncremental=false` нова справна копія зберігається без цього порівняння.

Також ураховуйте, що два запуски для одного пристрою в той самий каталог протягом однієї хвилини використовують однакове ім’я файла. Окремої версії для другого запуску не створюється.

Якщо цього дня виконувалося щомісячне архівування, перевірте й ZIP. У CLI-режимі одного пристрою нова копія також може опинитися всередині нього. Повні правила зберігання наведено в [BACKUPS.md](BACKUPS.md).

<a id="archive-problems"></a>
## Щомісячний архів не з’явився

Перевірте значення `MonthlyArchive` і дату запуску за місцевим часом хоста. `false` вимикає архівування, `true` або `1` вибирає перший день, а число від `2` до `28` — потрібний день місяця.

У вибраний день час запуску значення не має. Якщо цей день пропущено, наступний звичайний запуск його не наздоганяє. Під час роботи через BackUP Master щомісячне архівування не виконується.

Якщо архівувати нічого, порожній ZIP не створюється.

### Де шукати ZIP

Ім’я архіву відповідає попередньому календарному дню. Наприклад, під час запуску 1 жовтня 2026 року це `30.09.2026.zip`:

| Режим | Розташування |
|---|---|
| Пакетний | `<BackupRoot>/<DeviceName>/archive/30.09.2026.zip` |
| Один пристрій через CLI | `<BackupRoot>/30.09.2026.zip` |

Назва каталогу `archive/` пишеться малими літерами. Повторний запуск того самого дня оновлює ZIP із тим самим іменем.

### Архівування завершилося помилкою

Для кодів `70` і `71` перевірте журнал пристрою, доступ до каталогу архівів, вільне місце й стан уже наявного ZIP. Місце потрібне і у сховищі, і в локальному `/tmp`.

На локальному диску каталог `archive/` має належати користувачеві скрипта й мати права `0700`. У пакетному режимі з перевіреним мережевим сховищем і `UseNetFolder=true` інший власник або права, призначені NAS, самі собою не є причиною відмови. Помилки сховища під час архівування також можуть давати код `64` або `65`.

Перевірити наявний архів можна командою, указавши його фактичний шлях:

```bash
unzip -t "/mnt/backup/mikrotik/Router-A/archive/30.09.2026.zip"
```

Вихідні файли не видаляються до збереження перевіреного ZIP. Якщо архів уже збережено, але частину вихідних файлів видалити не вдалося, залишаться і ZIP, і невидалені файли. Пошкоджений наявний архів автоматично не замінюється новим.

**Не видаляйте резервні копії та журнали, що залишилися, доки не перевірите вміст архіву.** Порядок архівування описано в [BACKUPS.md](BACKUPS.md#monthly-archive).

## Немає журналу або виведення на екран

За `LogLevel=0` і відсутності помилок нові журнали не створюються. В інших випадках перевірте вибрані `BackupRoot`, `MainLogPath` і права запису.

Порожній `MainLogPath=` залишає `main.log` у `BackupRoot`. Якщо задано окремий каталог, він має вже існувати й бути доступним користувачеві скрипта. Журнали пристроїв цей параметр не переміщує.

Після щомісячного архівування попередня історія пристрою міститься в ZIP. Подальша робота записується до нового журналу поруч із копіями.

Під час запуску з планувальника або з перенаправленням виведення екранного журналу з індикатором і кольоровими позначками немає. Файлові журнали від цього не вимикаються.

Помилка запису журналу не зупиняє саме резервне копіювання, але відображається в результаті запуску як попередження. Докладніше дивіться в [LOGGING.md](LOGGING.md).

<a id="language-problems"></a>
## Переклад не застосувався

Перевірте вибрану мову й розташування файла. Наприклад, для `Language=de` потрібен читабельний звичайний файл `de.lang` поруч із `mikrotik-backup.sh`, а не в каталозі `lang/`. Символічне посилання як файл перекладу не використовується.

За `Language=auto` мова визначається за середовищем ОС. Для одного запуску її можна вказати явно, наприклад під час перегляду довідки:

```bash
mikrotik-backup.sh --language=de --help
```

Неперекладені повідомлення виводяться англійською. Непридатні рядки файла пропускаються. Файли `ru.lang` і `en.lang` не замінюють вбудовані переклади.

Формат рядків, імена ключів і правила підключення описано в [LOCALIZATION.md](LOCALIZATION.md).

<br />

## Налаштування не застосовується

Перевірте ім’я параметра, допустиме значення й повторні записи в `option.cfg`. Якщо параметр повторюється, використовується останнє придатне значення. Регістр ключів не враховується, але дефіс і підкреслення не є взаємозамінними.

Параметр, переданий через CLI, замінює відповідне значення з файла. Для звичайних запусків одного пристрою та пакетних запусків порядок такий:

**Вбудовані значення** → **Придатні рядки option.cfg** → **CLI**

BackUP Master має власний порядок заповнення форми: звичайні поля беруться з вбудованих значень і CLI, а не з файла параметрів. Виняток — `UseIncremental`. Налаштування журналювання з файла під час виконання через BackUP Master також ураховуються.

Правила читання параметрів наведено в [OPTIONS.md](OPTIONS.md), а особливості BackUP Master — в [INTERACTIVE.md](INTERACTIVE.md).

## Коди завершення

| Код | Значення |
|---:|---|
| `0` | Успіх без збережених помилок або попереджень |

Якщо повторна спроба отримання файла завершилася успішно, етап може закінчитися з `[OK]`, хоча помилка першої спроби залишиться в журналі. Ненульовий підсумковий код пакетного запуску також не означає, що не вдалося скопіювати всі пристрої: переглядайте результат кожного окремо.

Для коду `80` зверніть увагу на системні вимоги: GNU Bash 4.4 або новіший і працездатну локаль `C.UTF-8`. Докладніше дивіться в [INSTALL.md](INSTALL.md#вимоги-до-хоста).

## Якщо потрібна допомога

Укажіть версію скрипта, ОС і Bash, спосіб запуску, код завершення та додайте фрагмент журналу, що стосується помилки. Для проблеми з одним пристроєм потрібен його журнал, для помилки підготовки запуску — передусім `main.log`.

**Не надсилайте справжні паролі та повні робочі файли налаштувань.** Перед надсиланням перевірте журнали, знімки екрана й команди на наявність конфіденційних даних. Особливості захисту паролів описано в [SECURITY.md](SECURITY.md).

Зв’язатися з автором можна за контактами в [описі продукту](../README_UK.md#звязатися-з-автором).

# Конфігурація

[Зміст](../README_UK.md)

## Кілька слів на початку

Необов’язковий файл `option.cfg` дає змогу змінити стандартні налаштування скрипта.
Щоб скрипт завантажив перелічені в ньому налаштування під час виконання, `option.cfg` має бути поруч із `mikrotik-backup.sh` у тому самому каталозі.

Структура файла дуже проста: перелік даних у форматі `Ключ=значення`. Це не shell-скрипт.
Підстановлення змінних і виконання команд у ньому не відбуваються.

## Придатність конфігурації для запуску

Навіть один коректний розпізнаний рядок робить конфігурацію придатною.
Повний набір налаштувань перелічувати не потрібно: якщо стандартне значення певного параметра вас влаштовує, його можна не додавати до `option.cfg`.

Але якщо файл порожній або містить лише коментарі, невідомі ключі чи непридатні значення, скрипту нічого з нього завантажувати.
Тоді налаштування залишаються стандартними.

**І тут є нюанс!!!**
Якщо в такому стані запустити скрипт без аргументів, резервне копіювання не почнеться. Натомість скрипт спробує відкрити Configuration Editor.
Те саме відбудеться, якщо файла `option.cfg` взагалі немає.
Збережіть потрібні налаштування й запустіть скрипт повторно.
*(N.B. Для відкриття редактора потрібен термінал. Якщо такий запуск відбувається без термінала, наприклад із планувальника, скрипт завершиться з помилкою `31`. Підготуйте `option.cfg` до налаштування автоматичного запуску.)*

**Порядок читання необов’язкових параметрів:**
Джерела параметрів мають пріоритет. Якщо `option.cfg` немає, застосовуються значення за замовчуванням, вбудовані в скрипт.
Якщо файл існує й успішно прочитаний, наведені в ньому <mark>коректні</mark> параметри замінюють відповідні стандартні значення.

І найголовніше!!! Якщо той самий параметр передано через CLI, пріоритет має саме значення з CLI.
Отже, для звичайного запуску одного пристрою та пакетного запуску порядок такий:
**Вбудовані значення** → **Придатні рядки option.cfg** → **CLI**

*(N.B. Відсутній файл і файл, який неможливо прочитати, — не те саме. Якщо `option.cfg` існує, але скрипт не може його прочитати, виконання завершиться помилкою конфігурації з кодом `21`, а не продовжиться зі стандартними налаштуваннями.)*

## Як читається файл

Кожний рядок ділиться за першим `=`. Регістр у назвах ключів не враховується, але дефіс і підкреслення не є взаємозамінними.
Порожні рядки й рядки, у яких перший непробільний символ — `#`, ігноруються. Невідомий або непридатний рядок не скасовує коректних сусідніх рядків.
Якщо ключ повторюється, використовується останнє придатне значення.

У звичайних значеннях початкові й кінцеві пробіли видаляються.
**Важливо:** для `Login`, `Password` і `encrypt` усе після першого `=` зберігається буквально.
Не додавайте лапки за правилами shell: вони стануть частиною значення.
Не додавайте коментар після пароля. Для коментаря використайте окремий рядок.

Підтримуються один BOM на початку файла й закінчення рядків CRLF.
Дозволено читабельне символічне посилання на звичайний файл.
Проблема доступу або непридатний тип об’єкта не прирівнюються до порожнього файла й спричиняють помилку конфігурації.

## Створення, редагування та збереження файла 'option.cfg'

Найпростіший спосіб створити файл — запустити скрипт із параметром `-e`:

```bash
./mikrotik-backup.sh -e
```

Відкриється Configuration Editor із переліком основних параметрів.
Якщо всі рядки не вміщаються у вікні термінала, список автоматично прокручується під час руху стрілками вгору та вниз.
Пункти «Зберегти» й «Скасувати» розташовано наприкінці того самого списку.
Переходимо пунктами меню, указуємо потрібні параметри → вибираємо «Зберегти» → і (ви неперевершені) файл створено.

Під час роботи з інтерактивним меню редактор змінює налаштування лише в пам’яті.
Тільки після вибору «Зберегти» буде записано повний, *канонічний* файл.

Якщо `option.cfg` ще немає, редактор спочатку заповнює поля стандартними значеннями.
Якщо файл уже створено й ви змінили деякі параметри, Configuration Editor заповнить поля вашими значеннями, а не стандартними.

Другий спосіб створити 'option.cfg' — вручну. Так, відкриваємо улюблений текстовий редактор власноруч і вводимо потрібні налаштування.
Де їх узяти? Просто нижче:

## Налаштування та стандартні значення

| Ключ | За замовчуванням | Значення та призначення |
|---|---|---|
| `Language` | `auto` | `auto` або дві ASCII-літери, наприклад `ru`, `en`, `de` |
| `SshPort` | `22` | Порт `1`–`65535`; прихований у Configuration Editor, видимий у BackUP Master |
| `UseOxidized` | `false` | Імпортувати пристрої з Oxidized |
| `IgnoreOxiAccess` | `true` | Дозволити попередній DeviceList після помилки читання або розбору Oxidized; лише файл |
| `OxidizedHome` | Порожньо | Каталог із `config` і `router.db` |
| `UseIdentityName` | `true` | Використовувати поточне RouterOS Identity як ім’я пристрою |
| `backup_type` | `both` | `configuration`, `binary` або `both` |
| `UseIncremental` | `true` | Порівнювати нову перевірену резервну копію з попередньою; за `false` зберігати кожну нову копію без порівняння |
| `export_format` | `compact` | `compact`, `terse` або `verbose` |
| `show_sensitive` | `true` | Додавати чутливі значення до `.rsc` |
| `encrypt` | Порожньо | Пароль шифрування `.backup`; порожнє значення означає відсутність шифрування |
| `encrypt_type` | `aes-sha256` | Фіксований алгоритм; лише файл |
| `clear_dns_cache` | `true` | Очистити DNS-кеш перед бінарною копією |
| `clear_console_history` | `true` | Очистити історію консолі перед бінарною копією |
| `BackupRoot` | `backups` | Кореневий каталог сховища копій |
| `UseNetFolder` | `false` | Вимагати окреме монтування в пакетному режимі |
| `MonthlyArchive` | `false` | Вимкнути архівування (`false`) або вибрати день місяця від `1` до `28` |
| `LogLevel` | `2` | Рівень `0`, `1`, `2` або `3` |
| `MainLogPath` | Порожньо | Лише каталог для `main.log`; порожнє значення означає поточний `BackupRoot` |
| `Login` | Порожньо | Спільний логін, успадкований порожніми полями DeviceList; лише файл |
| `Password` | Порожньо | Спільний пароль, успадкований порожніми полями DeviceList; лише файл |

За `Language=auto` мову інтерфейсу та журналів вибирає локаль ОС.
Для зовнішнього перекладу використовується її дволітерний код мови: наприклад, для `de_DE.UTF-8` потрібен файл `de.lang` поруч зі скриптом.
Якщо придатного перекладу немає, використовується англійська.

Для `MonthlyArchive` правило дещо інше: `false`/`no`/`0`/`off` вимикають архівування; `true`/`yes`/`1`/`on` означають перший день місяця; значення від `2` до `28` вибирають потрібний день.

Під час збереження через редактор до файла записується `MonthlyArchive=false` або вибране число.

Логічні параметри приймають `true`/`false`, `yes`/`no`, `1`/`0` і `on`/`off` без урахування регістру. Редактор записує `true`/`false`.

Поля `IgnoreOxiAccess`, `encrypt_type`, `SshPort`, `Login` і `Password` у Configuration Editor не відображаються.

Під час збереження файла редактор записує `IgnoreOxiAccess`, `encrypt_type` і `SshPort`.
`Login` і `Password` зберігаються лише тоді, коли ці рядки вже були в `option.cfg`, зокрема з порожніми значеннями.

Поля `SshPort`, `Login` і `Password` можуть бути корисними, якщо всі пристрої використовують однаковий SSH-порт і того самого користувача — ті самі ім’я та пароль. Тоді в кожному записі `devicelist.cfg` достатньо лише двох значень: **імені** пристрою та його **IP-адреси**.

## Приклад без очищення та чутливих даних в експорті

Це приклад вибраної політики, **а не перелік заводських значень**:

```ini
Language=ru
SshPort=22
UseOxidized=false
IgnoreOxiAccess=true
OxidizedHome=
UseIdentityName=true
backup_type=both
UseIncremental=true
export_format=compact
show_sensitive=false
encrypt=
encrypt_type=aes-sha256
clear_dns_cache=false
clear_console_history=false
BackupRoot=backups
UseNetFolder=false
MonthlyArchive=false
LogLevel=2
MainLogPath=
```

Перші 19 ключів наведено в канонічному порядку запису.
Наявні сумісні рядки `Login` і `Password` зберігаються після них.

Відсутні налаштування використовують вбудовані значення, а не значення із сусіднього прикладу. Наприклад, файл, що містить лише `Language=ru`, не вимикає очищення й не змінює `show_sensitive=true`.

## Шляхи

```ini
BackupRoot=backups
MainLogPath=logs
```

Ці записи означають каталоги `backups` і `logs` поруч зі скриптом.
Абсолютні шляхи зберігають своє значення. `$HOME` і `~` не розкриваються як змінна або домашній каталог.

Відсутній `BackupRoot` створюється під час виконання, якщо це дозволяють права.
Кореневий каталог файлової системи `/` заборонено використовувати як сховище.
Для наявних каталогів програма не виправляє власника й права автоматично.

Непорожній `MainLogPath` має вказувати на **вже наявний каталог, доступний для запису**.
Створення самого `main.log` відкладається до першого запису; це не створює його батьківський каталог.
Якщо журнал неможливо записати, резервне копіювання триває з попередженням. Цей параметр не переміщує журнали пристроїв.

## Мережеве й окреме сховище

`UseNetFolder=true` діє в пакетному режимі. Шлях має належати до запису монтування, відмінного від запису для `/`.
Окремим сховищем може бути мережеве сховище, локальний диск або bind mount; назва параметра не обмежує тип файлової системи.

Звичайний каталог на тій самій кореневій файловій системі не відповідає цій вимозі.
Скрипт перевіряє доступність і монтування, але не викликає `mount`, `umount` або `sudo` й не перемикається непомітно на локальне запасне сховище.

## Пов’язані параметри

За `UseIncremental=false` скрипт не порівнює нову резервну копію з попередньою та зберігає кожний новий успішно створений і перевірений файл.
Це налаштування не впливає на отримання копій або щомісячне архівування.
За замовчуванням `UseIncremental=true`. Якщо у вашому `option.cfg` цього параметра ще немає, порівняння залишається ввімкненим.

`backup_type=configuration` не використовує шифрування бінарної копії та очищення перед нею. `backup_type=binary` не використовує `export_format` або `show_sensitive`. `UseOxidized=false` не використовує `OxidizedHome`.

За `UseIdentityName=true` помилка читання Identity не замінюється на `--device-name` або ім’я з DeviceList. Щоб використовувати задане ім’я, вимкніть `UseIdentityName`: дивіться [правила іменування](DEVICES.md#device-names).

За `MonthlyArchive=true` архівування виконується під час запуску скрипта у вибраний день місяця за місцевим часом хоста. Час запуску протягом цього дня значення не має.
Якщо цього дня скрипт не запускався, пропущене архівування не наздоганяється.

Які файли потрапляють до архіву, де він створюється та як отримує ім’я, описано в [BACKUPS.md](BACKUPS.md#monthly-archive).
Період, межу даних і пропущені спроби також визначено в [BACKUPS.md](BACKUPS.md#monthly-archive).

Конфігурація може містити секрети. Обмежте доступ до неї й не додавайте її до публічного репозиторію: [SECURITY.md](SECURITY.md).

## Версия 2.3.2

**Ориентировочная дата релиза: зима 2027 года.**

| Изменение | Что должно получиться |
|---|---|
| **SSH-аутентификация по ключам (первый и основной приоритет)** | SSH-ключи становятся основным способом по умолчанию. Вход по паролю через `sshpass` остаётся доступен только по явному выбору администратора и под его ответственность |
| Первый запуск и новый «Мастер настройки» | При запуске без аргументов, когда одновременно отсутствуют `option.cfg` и `devicelist.cfg`, сразу открывается пошаговый мастер настройки, а не главное меню или отдельный редактор конфигурации |
| Короткие и длинные ключи | У коротких ключей появляются соответствующие длинные формы, а у длинных, где возможно, короткие |
| Формат `devicelist.cfg` | Убирается ненужный «Маркер устройства» |
| Имя из круглых скобок | Извлечение становится опциональным, с возможностью использовать полное имя |

Перед первым шагом нового мастера показывается предупреждение «Система НЕ готова к пакетному копированию». Мастер также будет доступен отдельным пунктом главного меню и не заменит существующий мастер резервного копирования одного устройства. Ручная подготовка доступа и заполнение файлов остаются полноценной альтернативой; обязательного прохождения мастера для вручную настроенного скрипта не требуется.

Переход на SSH-ключи включает документированную подготовку ключевой пары на сервере резервного копирования, загрузку только публичного ключа на MikroTik и его привязку к пользователю, а также использование выбранного способа аутентификации для SSH-команд и получения файлов. В ключевом режиме `sshpass` не должен быть обязательной зависимостью; автоматического перехода на пароль при ошибке ключа не предусматривается.

Если Oxidized уже использует SSH-ключи, скрипт использует именно существующий ключевой доступ. В этой ветке генерация новых ключей на сервере и загрузка/импорт публичных ключей на устройства заблокированы; рабочая схема Oxidized не изменяется. Недоступность существующего ключа требует действия администратора, а не автоматической замены ключа. Подготовка нового ключевого доступа через первоначальный пароль является отдельным сценарием мастера.

Для подключения с `StrictHostKeyChecking=yes` необходимо заранее проверить ключ самого роутера и внести его в `known_hosts`. Проверка подлинности роутера и выбор способа входа являются разными настройками безопасности: выбор пароля сам по себе не означает отключение проверки ключа хоста. Точные параметры конфигурации, UI/CLI, порядок перехода со старых списков устройств и поддерживаемые версии RouterOS будут определены при проектировании. Это план версии 2.3.2, а не описание уже реализованной возможности 2.3.1.

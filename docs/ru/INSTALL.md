# Установка

[Оглавление](../README_RU.md)

## Требования к хосту

Для запуска требуются ОС Linux с GNU Bash **4.4 или новее** и стандартные GNU-утилиты для работы с файлами.  
Сам скрипт не требует компиляции, Python, контейнера или базы данных.  
Но требуется наличие утилит, перечисленных в разделе [Зависимости](#зависимости).

Для имён устройств требуется работающая локаль **`C.UTF-8`**: подсчёт многобайтовых символов, распознавание букв и приведение регистра. 
Скрипт проверяет эти возможности перед работой с устройствами. Это системное требование, а не отдельная программа с именем `C.UTF-8`.  

Разумеется, хосту требуются предварительно настроенный сетевой доступ к SSH-службе RouterOS и права записи в выбранное хранилище.  

**Строго рекомендуется!!!**  
Для подключения к устройствам под управлением RouterOS используется SSH с парольной аутентификацией, а не аутентификацией по ключам. 
(*Точную политику транспорта см. в [SECURITY.md](SECURITY.md).*)  
Поэтому рекомендуется создание на устройстве отдельного пользователя с ограничением его авторизации по IP-адресу хоста, на котором выполняется данный скрипт.

## Зависимости
### Обязательные для резервного копирования

Для выполнения резервного копирования необходимы **все** перечисленные утилиты:

| Утилиты | Назначение |
|---|---|
| `ssh`, `scp`, `sshpass` | Подключение к RouterOS, выполнение команд и получение файлов |
| GNU `timeout`, `sleep` | Ограничение времени выполнения операций и паузы |
| `sha256sum` | Вычисление контрольных сумм |
| `realpath` | Определение полных путей |
| `flock` | Блокировки, предотвращающие конфликт одновременных запусков |

**При обнаружении отсутствующей обязательной утилиты скрипт сообщает
о неудовлетворённых зависимостях и прекращает попытку резервного копирования.
Код ошибки зависимостей: `30`. Это штатное поведение.**

Список одинаков для одиночного и пакетного копирования, независимо от того,
создаётся `.rsc`, `.backup` или оба формата.

Одного наличия команд недостаточно: установленный OpenSSH должен поддерживать
используемые параметры, включая режим legacy SCP, выбираемый ключом `scp -O`.
GNU `timeout` должен поддерживать `--signal` и `--kill-after`.
Эти возможности проверяются локально, без подключения к маршрутизатору.

<br />

### Необходимые для отдельных возможностей

Эти инструменты не входят в общий обязательный список. Они требуются,
только когда используется соответствующая возможность.

| Возможность | Что требуется | Что происходит при отсутствии |
|---|---|---|
| Пакетный режим с `UseNetFolder=true` | `findmnt` | Резервное копирование в этом режиме не начинается; ошибка зависимостей `30` |
| Запуск, в котором должна выполняться месячная архивация | Info-ZIP `zip`, `unzip`, GNU `mv` | Запуск останавливается на проверке зависимостей, до резервного копирования; ошибка `30` |
| Интерактивное меню, редактор конфигурации и BackUP Master | `stty` и терминал на стандартном вводе и выводе | Интерактивный экран не открывается; ошибка терминала `31` |
| Copy console command в BackUP Master | GNU `base64` с поддержкой `--wrap=0` | Копирование команды недоступно; ошибка `30` |

Например, отсутствие `zip` не мешает обычному копированию в запуске, в котором месячная архивация не требуется.  
Отсутствие `base64` не мешает создавать резервные копии.  
*(N.B. Но требуется при выборе действия **Copy console command**.)*


Общая проверка зависимостей выполняется перед резервным копированием, а не при каждом открытии программы.  
Поэтому справка, версия или меню могут быть доступны даже без установленных утилит резервного копирования.

<br />

### Базовое окружение Linux

Также предполагается наличие обычных системных команд для работы с файлами
и каталогами, например `date`, `stat`, `mkdir`, `cp`, `ln` и `rm`.

Они являются частью базового окружения ОС. Перечисленный выше список
предварительно проверяемых зависимостей не является полным перечнем
всех внешних команд, используемых скриптом. Отсутствие базовой системной
команды может проявиться как ошибка соответствующей операции,
а не как сообщение о неудовлетворённых зависимостях.

## Получение файлов скрипта

Основной способ установки версии 2.3.1 — полный asset GitHub Release `mikrotik-backup-2.3.1.zip`. Он распаковывается непосредственно в каталог установки без дополнительного каталога-обёртки.
*(N.B. В примерах с размещением файлов под `/opt` выполняйте команды с правами на создание и запись в этот каталог.)*

### Вариант 1. Полный пакет релиза

Скачайте `mikrotik-backup-2.3.1.zip` из GitHub Release MikroTik Backup Script 2.3.1 и выполните:

```bash
mkdir -m 700 -- /opt/mikrotik-backup
unzip -q -- mikrotik-backup-2.3.1.zip -d /opt/mikrotik-backup
cd -- /opt/mikrotik-backup
sha256sum --check SHA256SUMS
```

После распаковки готовая к работе структура имеет вид:

```text
mikrotik-backup.sh
SHA256SUMS
README.md
lang/
docs/
```

Если проверка контрольной суммы завершилась ошибкой, не запускайте скрипт, пока не выясните причину.

<br />

### Вариант 2. Минимальная автономная установка

Скачайте assets `mikrotik-backup.sh` и `SHA256SUMS` из того же Release в защищённый каталог, проверьте их и сделайте скрипт исполняемым:

```bash
mkdir -m 700 -- /opt/mikrotik-backup
cd -- /opt/mikrotik-backup
# Скачайте оба asset релиза в этот каталог.
sha256sum --check SHA256SUMS
chmod 700 -- mikrotik-backup.sh
```

Для внешнего runtime-языка используйте полный пакет либо возьмите соответствующий файл `.lang` из исходников с тегом той же версии.

<br />

### Расширенный вариант: Git или архив исходного кода

Git-клон или архив **Code → Download ZIP** этого репозитория также является полным деревом исходного кода продукта. Полезная структура в корне:

```text
mikrotik-backup.sh
README.md
lang/
docs/
```

`SHA256SUMS` является артефактом Release и может отсутствовать в копии исходного дерева. Для обычной установки по-прежнему рекомендуется версионный пакет Release: он содержит файл контрольной суммы и точно соответствует опубликованной версии.

## Файлы рядом со скриптом

После распаковки полного пакета Release выбранный каталог содержит скрипт и сопутствующие файлы:

```text
mikrotik-backup/
├── mikrotik-backup.sh
├── SHA256SUMS
├── README.md
├── lang/
└── docs/
```

| Файл или каталог | Назначение |
|---|---|
| mikrotik-backup.sh | Сам скрипт резервного копирования |
| SHA256SUMS | Контрольные суммы для проверки полученных файлов |
| README.md | Описание программы и ссылки на подробную документацию |
| lang/ | Набор файлов локализаций. Скопируйте нужный языковой файл из этого каталога в каталог скрипта. |
| docs/ | Подробная документация по установке, настройке и использованию |

Для реальной работы Вам нужен только сам файл `mikrotik-backup.sh`.  
В случае необходимости изменения настроек рядом с ним следует создать и разместить файл настроек **option.cfg**.  
И если планируется опрос и снятие резервных копий с нескольких устройств подряд, также рядом со скриптом следует создать файл списка устройств **devicelist.cfg**.  
Файл локализации `<xx>.lang` нужен, если Вы хотите видеть меню и записи в логах на родном для Вас языке. Его также следует разместить в каталоге размещения `mikrotik-backup.sh`.  
Для русского и английского языков отдельный файл локализации не нужен: они встроены в тело скрипта.

**Запустив скрипт в интерактивном режиме, можно создать и сохранить:**  
Список устройств – **devicelist.cfg** через «BackUP Master».  
Файл конфигурации – **option.cfg** через «Редактор конфигурации».  
Или подготовьте их самостоятельно:    
*Файл списка устройств в формате TSV подробно описан в документе [DEVICES.md](DEVICES.md).*  
*Файл конфигурации в формате `Ключ=значение` подробно описан в документе [OPTIONS.md](OPTIONS.md).*

## Подготовка хранилища и журнала

При выполнении резервного копирования с настройками по умолчанию скрипт создаст рядом с собой каталог `./backups` и уже в него будет складывать резервные копии устройств.  
Разница будет лишь в том, что в «Одиночном режиме» созданные файлы размещаются непосредственно в каталоге `./backups`, а в «Пакетном режиме» внутри `./backups` создаётся подкаталог с именем устройства, в который и сохраняются его бэкапы.  

Необходимые каталоги хранилища скрипт создаёт самостоятельно с соответствующими правами доступа.  
*(У уже существующих администраторских каталогов скрипт автоматически не меняет владельца и режим доступа.)*

По умолчанию основной журнал скрипта `main.log` размещается в каталоге `./backups`.  
В пакетном режиме журнал работы с устройством находится в подкаталоге соответствующего устройства.

Также следует знать: если каталог, в который Вы будете складывать резервные копии, является сетевым,  
скрипт при пакетной обработке умеет проверять подобный каталог на доступность, но эта опция является отключённой «по умолчанию», и для её использования необходима соответствующая настройка.  
*(Способ монтирования этого каталога при этом не важен.)*  

Все эти опции могут быть изменены с помощью указания нужных параметров в файле `option.cfg`.  
Как это сделать и каков синтаксис этих параметров, можно узнать непосредственно в разделе [Конфигурация](OPTIONS.md).

## Автоматический запуск скрипта
Перед включением расписания должны быть подготовлены настройки и список устройств.  
Иначе автоматический запуск не сможет выполнить пакетное копирование.

Создавать отдельного пользователя для запуска скрипта не требуется, но в то же время выполнять подобные операции от **root** считается плохой практикой. Поэтому разберём вариант с созданием своего отдельного пользователя.

Создайте пользователя **bsmt** *(Вы можете использовать любое другое имя, заменив в примерах **bsmt** на удобное Вам)*, дав ему минимально необходимые права:
```bash
(
    set -e

    SCRIPT_DIR="/opt/mikrotik-backup"

    sudo useradd \
        --system \
        --user-group \
        --home-dir "$SCRIPT_DIR" \
        --no-create-home \
        --shell /usr/sbin/nologin \
        bsmt

    sudo chown bsmt:bsmt \
        "$SCRIPT_DIR" \
        "$SCRIPT_DIR/mikrotik-backup.sh"

    sudo chmod 0700 \
        "$SCRIPT_DIR" \
        "$SCRIPT_DIR/mikrotik-backup.sh"

    sudo find "$SCRIPT_DIR" -maxdepth 1 -type f \
        \( -name 'option.cfg' -o -name 'devicelist.cfg' -o -name '*.lang' \) \
        -exec chown bsmt:bsmt {} + \
        -exec chmod 0600 {} +
)
```

<br />


**Если скрипт уже запускался от root**

*(N.B. Если Вы ранее запускали скрипт от **root**, созданные им каталоги, 
резервные копии и журналы могут быть недоступны пользователю **bsmt**.
Перед включением расписания передайте ему существующее хранилище.)*

Пример тут указан для локального каталога `/opt/mikrotik-backup/backups`.  
Эта команда заменит владельца и группу каталога и его содержимого:
```bash
sudo chown -hR -P -- bsmt:bsmt "/opt/mikrotik-backup/backups"
```
*(N.B. Указывайте именно каталог резервных копий данного скрипта, а не общий каталог, содержащий данные других программ.
Если хранилище или основной журнал размещены отдельно, доступ к ним необходимо настроить отдельно, с учётом прав и настроек выбранного хранилища, по приведенному выше образцу.)*

Пример открытия «Редактора конфигурации» от имени **bsmt** после передачи ему прав на каталог и файлы скрипта:  
*(N.B. Команду выполняет root либо пользователь, которому разрешён такой запуск через sudo.)*
```bash
sudo -u bsmt /usr/bin/bash /opt/mikrotik-backup/mikrotik-backup.sh -e
```

**Создание планировщика запуска скрипта**

Далее рассматривается вариант создания планировщика с помощью systemd,  
но Вы можете использовать crontab или любой другой удобный Вам способ.

Итак, создадим сервис, выполняющий скрипт от нашего пользователя, и таймер, запускающий его по расписанию.  
*(Зададим тут ежедневный запуск в час ночи, но всё опять же в Ваших руках.)*

```bash
(
    set -e

    sudo tee /etc/systemd/system/mikrotik-backup.service >/dev/null <<'EOF'
[Unit]
Description=MikroTik backup
Wants=network-online.target
After=network-online.target

[Service]
Type=oneshot
User=bsmt
Group=bsmt
WorkingDirectory=/opt/mikrotik-backup
ExecStart=/usr/bin/bash /opt/mikrotik-backup/mikrotik-backup.sh
Environment="PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"
UMask=0077
NoNewPrivileges=true
Restart=no
TimeoutStartSec=infinity
StandardInput=null
StandardOutput=journal
StandardError=journal
EOF

    sudo tee /etc/systemd/system/mikrotik-backup.timer >/dev/null <<'EOF'
[Unit]
Description=Daily MikroTik backup

[Timer]
OnCalendar=*-*-* 01:00:00
AccuracySec=1s
Persistent=false
Unit=mikrotik-backup.service

[Install]
WantedBy=timers.target
EOF

    sudo chmod 0644 \
        /etc/systemd/system/mikrotik-backup.service \
        /etc/systemd/system/mikrotik-backup.timer

    sudo systemd-analyze verify \
        /etc/systemd/system/mikrotik-backup.service \
        /etc/systemd/system/mikrotik-backup.timer

    sudo systemctl daemon-reload
    sudo systemctl enable --now mikrotik-backup.timer

    systemctl list-timers --all mikrotik-backup.timer
)
```

*`Persistent=false` не включает догоняющий запуск после периода, когда таймер был выключен.  
`Restart=no` не назначает автоматических перезапусков сервиса после ошибки.*
